# Рабочий процесс агента

Один кейс ведёт один главный IDE-агент. Сбор сведений можно передать отдельному субагенту по `SUBAGENTS.md`; состояние кейса сохраняет только главный агент. Изменения состояния проходят через CLI. Черновики можно редактировать до сохранения. `--expect` берётся из `status` перед записью и защищает от перезаписи работы другого сеанса.

| Этап | Действие агента | Переход |
|---|---|---|
| `brief` | Переведи запрос в конкретное решение и назови адресата, цель, ограничения, источники и вопросы, способные изменить выбор. Если задача зависит от времени, зафиксируй момент анализа и периоды сравнения. Уточни только блокирующее допущение. | Сохрани новый бриф с `require_question_results: true`. |
| `research` | Проверь доступы, импортируй материалы, сопоставь версии, единицы, периоды, даты среза, определения, сегменты и знаменатели. Для каждого существенного вывода найди проверяемый диапазон. Заполни результаты по вопросам брифа. | После содержательной сверки сохрани факты и пробелы с их влиянием на выбор. При отсутствии источников согласуй получение материалов. |
| `options` | Рассмотри сохранение текущего решения, закрытие и минимум одно изменение. Сравни при одних ограничениях. У каждого варианта сформулируй сильнейшее возражение и объясни, за счёт чего меняются доходы и затраты. | Сохрани варианты и условия выбора. |
| `strategy` | Выбери вариант и согласуй продукт, коммуникации и проверку. Укажи механизмы, обеспечивающие каждое обещание. Зафиксируй метрику, базу сравнения, окно и порог. | Сохрани проверенный черновик и передай его отдельному проверяющему. После `clear` покажи отчёт через `report --for-owner`. |
| `decision` | Запиши явный выбор, основания и обязательства с владельцами, датами, метриками и условиями пересмотра. | При другом выборе сначала вернись к стратегии. |
| `monitor` | Проверь действующее решение и сроки через `followup`, запиши результат обязательства через `track`. При новых данных прочитай `impact` и `history`, обнови выводы и представь новую рекомендацию вместе с действующим решением. | Сопровождай действующие обязательства до следующего явного `decide` владельца. |

При продолжении начни с `context <кейс> --evidence`. Он возвращает статус, бриф, проверенные метрики, ответы по вопросам и диапазоны ссылок. Для проверки смысла открывай только нужные диапазоны снимков или дополнительные поля этапа.

Проверь, какие вопросы способны изменить выбор и какие материалы их закрывают. Сопоставляй доли по одинаковым определениям и завершённым окнам. В `comparability` запиши условия, которые можно проверить по таблице. Для неполной когорты покажи наблюдаемую долю с её знаменателем. При отсутствии полной величины укажи пробел или ограничение для наблюдения. Если проверка оставила порог без оценки, передай в `options` ближайший шаг для получения сопоставимых данных. В `strategy` учти эти условия при рекомендации запуска.

## Выбор глубины и инструмента

- **Быстрый разбор.** Для обратимого решения с качественным брифом начни с локальных материалов. Проверь главную метрику и одно альтернативное объяснение. Сильную модель используй для финального сравнения, если оно действительно неоднозначно.
- **Исследование.** Если от одного неизвестного зависит выбор, сначала измерь его. Для таблицы используй `rates`, для поиска текста — `find`, для точных ссылок — `view`. Сохраняй доли через `rate_checks` и подставляй их в вывод через `{{rate:1}}`. Команда `claim` показывает готовую формулировку и фрагменты материалов. Уточняй, независимы ли источники. Публичная справка о конкуренте подтверждает его механику, но не переносится на продукт кейса.
- **Повышенная цена ошибки.** Перед закрытием или большим бюджетом найди самое сильное возражение к рекомендованному варианту. Проверь, выдерживает ли рекомендация правдоподобное изменение ключевого допущения. Запроси решение владельца и факты, которых не хватает.
- **Сбой.** Сначала `recover`: он читает состояние и черновики без модели и сети. Если файл завершён, выполни `check`, содержательную сверку и `save` с актуальной ревизией. Невалидный или частичный JSON не считается этапом. Не повторяй уже сохранённое действие. После двух подряд сетевых ошибок остановись, назови сохранённый результат и точное препятствие. При сетевом сбое источника используй только разрешённую локальную копию с URL.
- **Стоимость.** Фиксируй известные секунды, токены, стоимость и исход обычного сеанса через `log`. Включай повторы и помощь человека. Для `qwen-run` фактические токены записываются отдельно в `qwen_usage` из ответа провайдера. Цена отсутствующего измерения неизвестна. Интервалы между сохранениями включают время инструментов и человека. [Токенный бюджет](../docs/BUDGET.md)

## Структура хранения

- `AGENTS.md`, `agent/` — постоянные инструкции, этапы и контракт артефактов.
- `knowledge/` — методы. Прежний вывод агента здесь не становится фактом.
- `cases/<кейс>/materials/` — разрешённые входные файлы. CLI хранит отдельные неизменяемые текстовые снимки и их хеши.
- `cases/<кейс>/state.sqlite3` — текущее состояние, снимки, история решений, журнал. `context`, `history`, `journal` и `report` показывают его в текстовом виде.
- `cases/<кейс>/drafts/` — редактируемые артефакты до проверки. Сохраняй их по этапам и версиям. Непроверенные черновики не заменяют состояние кейса.

Перед независимым чтением сверь план с исходным сигналом, основания денежного механизма и единые условия запуска и пересмотра во всех разделах. Отметь оценки и предварительные пороги как допущения. После `save strategy` зафиксируй вердикт отдельного проверяющего. Каждая исправленная версия проходит такую же проверку. [Передача и разбор замечаний](../docs/STRATEGY_REVIEW.md)

Для переноса останови запись и скопируй папку кейса вместе с репозиторием. Для продолжения в новом чате назови ID кейса. Если пользователь изменил задачу, архивируй зависимые этапы через `reopen` с причиной.

## Новые материалы

Замена или отзыв снимка, на который ссылается исследование, автоматически открывает пересмотр. Для добавленного материала после сохранённого исследования CLI показывает `pending_source_reviews`. Сверь материал с вопросами брифа, метриками и условиями пересмотра. Запиши оценку через `review-source` с причиной и актуальной ревизией. При `--outcome relevant` используй `--claims` для затронутых выводов, `--questions` и `--metrics` для затронутых вопросов и метрик брифа. Указывай вопрос или метрику напрямую, когда источник заполняет пробел. Если меняется условие выбора и для нового наблюдения нужен новый ID, укажи это в причине.

Оценка `irrelevant` закрывает оценку с текущим этапом. Оценка `relevant` открывает `research`. Используй `context <кейс> --review`, чтобы получить состояние, прежнюю рекомендацию и `review.draft` из архивной ревизии. При прежнем брифе черновик содержит незатронутые факты с действующими источниками и связанные с ними проверенные метрики и ответы. Сверь область применимости, добавь новые выводы и заполни сопоставление и пробелы. Для полного архивного артефакта используй `history`. После сохранения исследования сверь изменения метрик в `report` или `context --evidence`. Действующее решение утверждается отдельно через `decide`, его обязательства доступны через `followup` во время пересмотра.
