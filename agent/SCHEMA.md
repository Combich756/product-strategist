# Формат артефактов

Каждый артефакт — JSON-объект UTF-8. Тексты в полях непустые. Примеры по всем этапам лежат в [demo/checkpoints](../demo/checkpoints). Подставляй данные текущего кейса.

| Этап | Поля |
|---|---|
| `brief` | Строки `question`, `goal`, `audience`, `constraints`, `available_data`, список строк `questions`, флаг `require_question_results` для нового брифа, объект `analysis` для задач с датами и список `metrics` для показателей решения. |
| `research` | Строка `comparison`, список строк `gaps`, список `claims`, объект `metrics` для показателей и `question_results` для вопросов из брифа. |
| `options` | Строка `comparison`, список `options`. |
| `strategy` | Строки `option` (ID варианта), `rationale`, `revisit`; объекты `product`, `communication`, `test`. |
| `decision` | Строки `option` (ID рекомендованного варианта), `approved_by`, `rationale`; список `commitments`. |

## Время анализа

Возьми `analysis.as_of` и `analysis.timezone` из `context`. Для относительных дат запиши в `brief.analysis` конкретные периоды. `as_of` содержит время ISO 8601 со смещением. `timezone` задаёт часовой пояс IANA, `UTC` или фиксированное смещение. Даты `start` и `end` включают обе границы, а `label` различает периоды. Если период пока неизвестен, оставь `periods` пустым и обозначь пробел. Брифы без `analysis` используют сохранённый момент анализа кейса.

```json
{
  "as_of": "2026-11-08T12:00:00+00:00",
  "timezone": "UTC",
  "periods": [
    {"label": "W41", "start": "2026-10-05", "end": "2026-10-11"},
    {"label": "W42", "start": "2026-10-12", "end": "2026-10-18"}
  ]
}
```

`sources`, `view` и `claim` показывают `timing` сохранённой версии источника. `timing.period` описывает охват данных, `timing.data_as_of` — дату или момент среза, `timing.validity` — известные границы срока действия, `timing.timezone` — пояс календарных дат источника. Все границы календарных дат включительны. При нескольких сроках в одном документе укажи применимость конкретного факта в `limits` и сошлись на соответствующие строки. В архиве `claim --revision` использует момент анализа и версии источников той ревизии.

## Метрики решения

Добавь `metrics` в бриф, когда выбор зависит от показателей с известной структурой таблицы. Укажи `id` (`M1` и далее), название `label`, единицу `unit` и `formula` с именами столбцов. Для доли используй `numerator`, `denominator` и при необходимости `subtract`. Для показателя из одной числовой ячейки используй `column`. Заданный порог запиши в `threshold` с `op` (`>=` или `<=`) и числом `value` в единицах метрики. Для доли `value: 20` означает 20%. Поле `threshold` можно опустить, если порог ещё предстоит определить.

```json
"metrics": [
  {"id": "M1", "label": "Первые оплаты", "unit": "%",
   "formula": {"numerator": "paid", "denominator": "offers"}, "threshold": {"op": ">=", "value": 20}},
  {"id": "M2", "label": "Оплаты после возвратов", "unit": "%",
   "formula": {"numerator": "paid", "subtract": "refunded", "denominator": "offers"}},
  {"id": "M3", "label": "Сопровождение", "unit": "мин",
   "formula": {"column": "support_minutes"}, "threshold": {"op": "<=", "value": 480}}
]
```

В исследовании свяжи каждый ID с фактом и номером расчёта или ячейки, считая с единицы. Вид формулы определяет, какой список использует `check`: `rate_checks` для доли, `cell_checks` для ячейки. Для ячейки используй десятичное число в единицах брифа. Если не хватает данных или сопоставимого наблюдения, укажи `gap` с причиной и недостающим материалом.

```json
"metrics": {
  "M1": {"claim": "C9", "check": 1},
  "M2": {"claim": "C10", "check": 1},
  "M3": {"gap": "В выгрузке нет минут сопровождения. Нужен журнал команды."}
}
```

При записи исследования CLI сверяет полноту списка, формулы и ссылки на строки. `report` собирает таблицу из пересчётов и показывает, выполнен ли порог. Сравнение выполняется до округления. При замене снимка привяжи показатели к проверкам актуальных фактов.

Если результат можно применять к порогу только при заданной единице наблюдения, определении или составе знаменателя, добавь `comparability` к метрике в брифе. Объект содержит имена столбцов и требуемые строковые значения. Для счётчиков используй формат исходной таблицы, например `"0"`.

```json
{
  "id": "M5",
  "label": "D7 полной когорты",
  "unit": "%",
  "formula": {"numerator": "returned_d7", "denominator": "eligible_d7"},
  "threshold": {"op": "<=", "value": 50},
  "comparability": {"observation_unit": "account", "calculation_rule": "d7_calendar",
                    "denominator_scope": "closed_windows", "window_open": "0"}
}
```

CLI проверяет указанные условия во всех строках, использованных в расчёте этой метрики. Проверка читает тот же снимок. Значения столбцов, которых в нём нет, требуют отдельного подтверждения. Паспорт метрики задаёт смысл столбцов и требуемые условия.

| `comparability_check.status` | Результат |
|---|---|
| `compatible` | Все значения совпали. CLI оценивает порог для определённой числовой метрики. |
| `incompatible` | Найдено несовпадение. CLI сохраняет наблюдение, указывает строку и оставляет порог без оценки. |
| `unverified` | Требуемый столбец или значение отсутствует. CLI сохраняет наблюдение и оставляет порог без оценки. |

`check` возвращает эти детали в `metric_comparability`, а `report` и `context --evidence` показывают результат вместе с измерением. У неподтверждённой метрики из одной ячейки отображается исходное число без заявленной единицы. Условия можно указать и для метрики без порога. Для метрик без `comparability` действуют правила по формуле и порогу из брифа.

## Исследование

Новый бриф включает `require_question_results: true`. Вопросы `Q1`, `Q2` и далее следуют порядку строк в `brief.questions`. Для каждого вопроса в `research.question_results` укажи `decision_impact` и список существующих `claims` типа `fact` или `gap` вместе с `next_check`. Пробел тоже может ссылаться на факты, показывающие границу данных. До сохранения агент сверяет, отвечают ли факты на вопрос и верно ли описано влияние. Для прежних брифов без флага действует прежняя схема сохранения.

```json
"question_results": {
  "Q1": {"claims": ["C1"], "decision_impact": "В выборке видна просадка показателя из дашборда."},
  "Q2": {
    "gap": "Часть окон D7 ещё открыта.",
    "claims": ["C2"],
    "decision_impact": "Порог запуска применим после дозревания всей когорты.",
    "next_check": "Запросить повторный срез той же недели после закрытия окон."
  }
}
```

CLI проверяет наличие всех вопросов, ID фактов и поля пробела. Отчёт показывает основания, влияние и следующую проверку. `context --evidence` возвращает эти записи вместе с метриками и диапазонами ссылок.

`claims[]` содержит `id` (`C1` и далее), `type` (`fact`, `hypothesis`, `forecast`, `unknown`), `scope` (`case`, `public`, `demo`), `text`, `limits`, `refs`.

Ссылка имеет вид `{"source":"S002","start":2,"end":5}`. Нумерация строк с единицы, обе границы включительно. Сохраняй короткий диапазон из активного снимка. Для факта нужна хотя бы одна ссылка. Факт, основанный только на открытых источниках, получает `scope=public`. Любое утверждение со ссылкой на синтетический источник получает `scope=demo` и ограничивается демонстрацией. Для неизвестного можно передать пустой `refs`.

Сохраняй один и тот же ID при пересмотре смысла того же тезиса. Новый тезис получает новый ID. В `limits` указывай применимость и что могло бы изменить вывод.

Для выводов на основе `rates` добавляй в `claims[]` поле `rate_checks` со списком проверок. Каждая проверка фиксирует одну группу, исходные столбцы и ожидаемые счётчики.

Для любого нового вывода с цифрами в `text` и ссылкой на CSV, TSV или XLSX нужны `rate_checks` или `cell_checks` для каждого указанного табличного источника. Правило действует и для гипотез. Для долей выбирай `rate_checks`. Ячейки подходят для отдельных значений, дат и категорий. Смысл вывода проверяет агент.

```json
{
  "source": "S002",
  "group": {"week": "2026-W42"},
  "numerator": "connected_48h",
  "denominator": "eligible_orders",
  "expected": {"numerator": 236, "denominator": 400}
}
```

`group` содержит пары «столбец — значение» из вывода `rates`. Для итога по всей таблице передай `{}`. Укажи отдельную проверку для каждой сравниваемой группы. При проверке и сохранении CLI заново считает долю по сохранённому снимку. Каждая использованная строка должна входить в диапазон `refs` для того же снимка. Поле необязательно для текстовых источников и ранее сохранённых артефактов.

В новом выводе подставляй доли через ссылки в `text`. Например, `"W42 — {{rate:1}}"` с проверкой выше даст `W42 — 236/400 = 59%`. Номер ссылки — позиция в `rate_checks`, начиная с единицы. Для знаменателя 0 CLI покажет `0/0, доля не определена`. В одном таком выводе все дроби и проценты записывай через ссылки. `report` подставляет результаты, `claim` возвращает готовую формулировку в `rendered_text`, а `context --stage research` показывает исходный JSON для редактирования.

Для старых черновиков CLI также сверяет процент, записанный рядом с проверенными счётчиками, например `48/80 = 60%` или `48/80 магазинов (60%)`. Учитывается точность округления в тексте. Смысл вывода, выбор группы и отдельные числа в свободном тексте проверяет агент.

`rates <кейс> S002 --by week platform --numerator connected_48h --denominator eligible_orders --evidence` выдаёт готовые `refs` и `rate_checks`. Используй их в выводе целиком или выбери нужные группы вместе с их строками, без ручного пересчёта ссылок. Максимум 20 проверок долей на один вывод.

Для доли оплат после возвратов используй `rates <кейс> S003 --by segment --numerator paid --subtract refunded --denominator offers --evidence`. Столбец `refunded` вычитается из числителя в каждой строке. Проверка сохраняет формулу и повторяет расчёт по тем же строкам.

Для узкого вывода добавь `--group platform=Android` или несколько `--group столбец=значение`. Фильтр выбирает только поля из `--by` и сохраняет номера строк исходного снимка.

`cells <кейс> S002 --rows 3 5 --columns eligible_orders` выдаёт готовые `refs` и `cell_checks`. Пример проверки ячейки:

```json
{"source": "S002", "line": 3, "column": "eligible_orders", "expected": "100"}
```

`expected` — точное значение из снимка таблицы, `line` — физическая строка начала записи в снимке. Для XLSX `row` в `view` указывает на строку листа. Для многострочной ячейки ссылка должна включать всю запись. Максимум 200 ячеек на вывод. CLI сравнивает значение с неизменяемым снимком и проверяет покрытие ссылками.

## Варианты и стратегия

- `options[]` содержит `id` (`O1` и далее), `kind` (один `status_quo`, один `close`, минимум один `change`), `title`, `action`, `benefit`, `objection`, `economics` и список ID `claims`.
- `product` содержит `audience`, `job`, `alternatives`, `direction`, `tradeoffs`, `economics` и список ID `claims`.
- `communication` содержит `audience`, `situation`, `barrier`, `message`, `proof`, `channel_roles`, `promise_limit` и список ID фактов `proof_claims`. Для собственного обещания нужны правила или наблюдение о своём продукте. Факта о конкуренте для этого недостаточно.
- `test` содержит `expected`, `metric`, `denominator`, `control`, `window`, `threshold`, `guardrails` и список ID `claims`. Ожидаемый эффект обозначай отдельно от наблюдаемого результата.
- В `options` и `strategy` добавляй `assumptions`: список строк с основанием каждой оценки часов, прогноза или порога и способом её уточнения. Утверждённое ограничение из брифа отличается от предложенной оценки. Отсутствие `assumptions` вызывает предупреждение, поскольку CLI не определяет основания свободного текста автоматически.

## Проверка и восстановление

`check <кейс> <этап> <путь.json>` проверяет JSON, наличие предыдущих этапов, структуру, ссылки и объявленные расчёты без изменения кейса. Успешный `check` не утверждает решение и не гарантирует корректность рассуждений. При сохранении `save` выполняет те же проверки повторно и фиксирует хеш артефакта в журнале.

`recover <кейс>` показывает состояние и JSON-файлы из `drafts/`, различает завершённые и незавершённые этапы и предлагает команду сохранения подходящего черновика. Назови файлы `research.json`, `strategy-v2.json` и т. п. При паузе предлагается сначала `resume`. Команды не выполняются автоматически. Для `decision` команда утверждения автоматически не предлагается.

Старые сохранённые кейсы читаются без миграции. При повторном сохранении числового исследования потребуются объявленные проверки для табличных ссылок.

## Решение

`commitments[]` содержит `id` (`K1` и далее), `task`, `owner`, `due` (ГГГГ-ММ-ДД), `metric`, `trigger`. Записывай роль ответственного и только разрешённые идентификаторы. При отсутствии утверждения оставляй кейс на `decision`.

`status` и `followup` показывают `active_decision` с опцией, владельцем и ревизией утверждения. `under_review` означает, что этапы пересматриваются. `followup` включает обоснование и статусы действующих обязательств. После нового `decide` обязательства новой версии начинают со статуса `open`, даже если их ID совпадают с прежними. Итоговые статусы прежней версии доступны в `history` в поле `final_tracking`.

Валидация проверяет структуру, этап, ссылки, диапазоны и зависимости. Качество исследования, верность пересказа и достаточность доказательств проверяются агентом по материалам и человеком при решении.
