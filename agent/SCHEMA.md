# Формат артефактов

Каждый артефакт — JSON-объект UTF-8. Тексты в полях непустые. Примеры по всем этапам лежат в [demo/checkpoints](../demo/checkpoints). Подставляй данные текущего кейса.

| Этап | Поля |
|---|---|
| `brief` | Строки `question`, `goal`, `audience`, `constraints`, `available_data`, список строк `questions` и объект `analysis` для задач с датами. |
| `research` | Строка `comparison`, список строк `gaps`, список `claims`. |
| `options` | Строка `comparison`, список `options`. |
| `strategy` | Строки `option` (ID варианта), `rationale`, `revisit`; объекты `product`, `communication`, `test`. |
| `decision` | Строки `option` (ID рекомендованного варианта), `approved_by`, `rationale`; список `commitments`. |

## Время анализа

Возьми `analysis.as_of` и `analysis.timezone` из `context`. Для относительных дат запиши в `brief.analysis` конкретные периоды. `as_of` содержит время ISO 8601 со смещением. `timezone` задаёт часовой пояс IANA, `UTC` или фиксированное смещение. Даты `start` и `end` включают обе границы, а `label` различает периоды. Если период пока неизвестен, оставь `periods` пустым и обозначь пробел. Брифы без `analysis` используют сохранённый момент анализа кейса.

```json
{
  "as_of": "2026-11-08T12:00:00+00:00",
  "timezone": "UTC",
  "periods": [
    {"label": "W41", "start": "2026-10-05", "end": "2026-10-11"},
    {"label": "W42", "start": "2026-10-12", "end": "2026-10-18"}
  ]
}
```

`sources`, `view` и `claim` показывают `timing` сохранённой версии источника. `timing.period` описывает охват данных, `timing.data_as_of` — дату или момент среза, `timing.validity` — известные границы срока действия, `timing.timezone` — пояс календарных дат источника. Все границы календарных дат включительны. При нескольких сроках в одном документе укажи применимость конкретного факта в `limits` и сошлись на соответствующие строки. В архиве `claim --revision` использует момент анализа и версии источников той ревизии.

## Исследование

`claims[]` содержит `id` (`C1` и далее), `type` (`fact`, `hypothesis`, `forecast`, `unknown`), `scope` (`case`, `public`, `demo`), `text`, `limits`, `refs`.

Ссылка имеет вид `{"source":"S002","start":2,"end":5}`. Нумерация строк с единицы, обе границы включительно. Сохраняй короткий диапазон из активного снимка. Для факта нужна хотя бы одна ссылка. Факт, основанный только на открытых источниках, получает `scope=public`. Любое утверждение со ссылкой на синтетический источник получает `scope=demo` и ограничивается демонстрацией. Для неизвестного можно передать пустой `refs`.

Сохраняй один и тот же ID при пересмотре смысла того же тезиса. Новый тезис получает новый ID. В `limits` указывай применимость и что могло бы изменить вывод.

Для выводов на основе `rates` добавляй в `claims[]` поле `rate_checks` со списком проверок. Каждая проверка фиксирует одну группу, исходные столбцы и ожидаемые счётчики.

Для любого нового вывода с цифрами в `text` и ссылкой на CSV, TSV или XLSX нужны `rate_checks` или `cell_checks` для каждого указанного табличного источника. Правило действует и для гипотез. Для долей выбирай `rate_checks`. Ячейки подходят для отдельных значений, дат и категорий. Смысл вывода проверяет агент.

```json
{
  "source": "S002",
  "group": {"week": "2026-W42"},
  "numerator": "connected_48h",
  "denominator": "eligible_orders",
  "expected": {"numerator": 236, "denominator": 400}
}
```

`group` содержит пары «столбец — значение» из вывода `rates`. Для итога по всей таблице передай `{}`. Укажи отдельную проверку для каждой сравниваемой группы. При сохранении CLI заново считает долю по сохранённому снимку. Каждая использованная строка должна входить в диапазон `refs` для того же снимка. Поле необязательно для текстовых источников и ранее сохранённых артефактов. Сверка проверяет счётчики и строки. Связь чисел с выводом в поле `text` проверяет агент или человек.

`rates <кейс> S002 --by week platform --numerator connected_48h --denominator eligible_orders --evidence` выдаёт готовые `refs` и `rate_checks`. Используй их в выводе целиком или выбери нужные группы вместе с их строками, без ручного пересчёта ссылок. Максимум 20 проверок долей на один вывод.

Для узкого вывода добавь `--group platform=Android` или несколько `--group столбец=значение`. Фильтр выбирает только поля из `--by` и сохраняет номера строк исходного снимка.

`cells <кейс> S002 --rows 3 5 --columns eligible_orders` выдаёт готовые `refs` и `cell_checks`. Пример проверки ячейки:

```json
{"source": "S002", "line": 3, "column": "eligible_orders", "expected": "100"}
```

`expected` — точное значение из снимка таблицы, `line` — физическая строка начала записи в снимке. Для XLSX `row` в `view` указывает на строку листа. Для многострочной ячейки ссылка должна включать всю запись. Максимум 200 ячеек на вывод. CLI сравнивает значение с неизменяемым снимком и проверяет покрытие ссылками.

## Варианты и стратегия

- `options[]` содержит `id` (`O1` и далее), `kind` (один `status_quo`, один `close`, минимум один `change`), `title`, `action`, `benefit`, `objection`, `economics` и список ID `claims`.
- `product` содержит `audience`, `job`, `alternatives`, `direction`, `tradeoffs`, `economics` и список ID `claims`.
- `communication` содержит `audience`, `situation`, `barrier`, `message`, `proof`, `channel_roles`, `promise_limit` и список ID фактов `proof_claims`. Для собственного обещания нужны правила или наблюдение о своём продукте. Факта о конкуренте для этого недостаточно.
- `test` содержит `expected`, `metric`, `denominator`, `control`, `window`, `threshold`, `guardrails` и список ID `claims`. Ожидаемый эффект обозначай отдельно от наблюдаемого результата.
- В `options` и `strategy` добавляй `assumptions`: список строк с основанием каждой оценки часов, прогноза или порога и способом её уточнения. Утверждённое ограничение из брифа отличается от предложенной оценки. Отсутствие `assumptions` вызывает предупреждение, поскольку CLI не определяет основания свободного текста автоматически.

## Проверка и восстановление

`check <кейс> <этап> <путь.json>` проверяет JSON, наличие предыдущих этапов, структуру, ссылки и объявленные расчёты без изменения кейса. Успешный `check` не утверждает решение и не гарантирует корректность рассуждений. При сохранении `save` выполняет те же проверки повторно и фиксирует хеш артефакта в журнале.

`recover <кейс>` показывает состояние и JSON-файлы из `drafts/`, различает завершённые и незавершённые этапы и предлагает команду сохранения подходящего черновика. Назови файлы `research.json`, `strategy-v2.json` и т. п. При паузе предлагается сначала `resume`. Команды не выполняются автоматически. Для `decision` команда утверждения автоматически не предлагается.

Старые сохранённые кейсы читаются без миграции. При повторном сохранении числового исследования потребуются объявленные проверки для табличных ссылок.

## Решение

`commitments[]` содержит `id` (`K1` и далее), `task`, `owner`, `due` (ГГГГ-ММ-ДД), `metric`, `trigger`. Записывай роль ответственного и только разрешённые идентификаторы. При отсутствии утверждения оставляй кейс на `decision`.

Валидация проверяет структуру, этап, ссылки, диапазоны и зависимости. Качество исследования, верность пересказа и достаточность доказательств проверяются агентом по материалам и человеком при решении.
